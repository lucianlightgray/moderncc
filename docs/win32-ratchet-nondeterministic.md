`ast-verify-ratchet` on the **mingw / x86_64** (win32) CI cell has a nondeterministic gap set: the set of non-faithful (desync/unfaithful/stackresidue) functions the win32 mcc reports over `tests/exec/*.c` **changes run-to-run on identical source**. Observed 2026-07-28: 7 functions (`bounds/bound_setjmp.c check`, `expressions/lshift_type.c main`, `features_c99_c11/builtins.c main`, `lexical/utf8_string_literal.c main`, `preprocessor/conditional_inclusion.c main`, `structs_unions/struct_init.c foo`, `vla/label.c f2`) recorded as **desync** at commit c47a5d17 but **faithful** at 6a0e1f47 — and nothing between those commits touched their codegen.

**Why:** `tests/ast/verify_ratchet.cmake` demands an EXACT `(file,func)` set match (it FATAL_ERRORs on wins as well as regressions, line ~116). The win32 baseline is regenerated by the mingw build, which is `mcc-hosted-by-<mingw-gcc>`; that two-stage self-build is itself nondeterministic — the same class as [[data-rel-local-selfmiscompile]] (the mcc binary differs run-to-run), so the fidelity verdicts of the mcc it produces flicker. `x86_64-linux.txt` does NOT flake (verified locally in a linux/amd64 container: ratchet passes clean), so it is win32-self-build-specific.

**Implication:** a red mingw ast-verify-ratchet is often NOT a real recorder regression — check whether the drift is only wins, or functions unrelated to the change. It cannot be reliably greened by editing `x86_64-win32.txt` from a non-mingw host (I can only reverse-engineer the delta from CI logs, and it moves). Real fixes: address the win32 self-build nondeterminism, or relax the ratchet to fail only on NEW gaps (regressions), not on banked wins. Baselines are per-target under `tests/ast/verify-baseline/<cpu>-<os>.txt`; only x86_64-linux and x86_64-win32 exist (arm64 skips — no baseline).
