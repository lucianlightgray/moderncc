#### Running a sweep — use the targets, not a hand-built wrapper

Landed 2026-07-31. Every triple × libc is a CMake target, so the prefix is pinned in one place instead of being retyped per session:

```
cmake --build . --target journal-sweep-<key>          # cross-hosted, fast
cmake --build . --target journal-sweep-<key>-native   # under qemu-user / wine
cmake --build . --target journal-regen-<key>          # rebank (native by default)
cmake --build . --target journal-sweep-all            # whole matrix, keep-going
cmake --build . --target journal-sweep-report         # matrix summary + verdict
```

`<key>` is `<cpu>-<os>[-<libc>]`, e.g. `arm64-linux-glibc`, `i386-win32-ucrt`, `x86_64-linux-musl`. The *baseline* key is `<cpu>-<os>` alone — **libc is not a filename axis** (changed 2026-07-31). A non-default libc therefore has no bank of its own and skips with that reason; it does not score itself against the default libc's corpus, which would read as a verdict rather than as the gap it is. Reintroducing musl or msvcrt as a measurable axis means reintroducing a filename axis for it. Driver is `tests/ast/journal_sweep.cmake`; `tests/ast/journal_native.cmake` builds the target-native mcc that `-native` needs; `verify_ratchet.cmake` grew `MCCLAUNCH`/`MCCFLAGS`/`MCCPATHPREFIX` (the last exists because wine maps `/` onto `Z:`, so a PE mcc reads a bare unix path as a Windows one).

**Why this replaced the wrappers:** the prefix is the measurement. A hand-built wrapper that added one extra `-I$root/runtime/include` lifted i386-linux coverage from 261 files to 266 and reported `fix 31261 -> 32241` as a depth REGRESSION that did not exist. Keys that cannot run here still get a target and skip with the specific reason (outside the journal gate / no sysroot / needs macOS / libc not vendored) rather than silently measuring a narrower corpus — and `journal-sweep-report` counts keys that were never run separately from keys that passed, because a matrix listing only successes reads as full coverage.

**Baselines are keyed by header set, not by triple** — landed 2026-07-31 fixing CI. The same triple has *two* consumers measuring *two* corpora: the `ast-journal-parity` ctest cell compiles against whatever headers its machine has, and a sweep compiles against a vendored sysroot. The sysroot corpus is a superset — more of the 275 files compile — so both the depth ceiling and the honesty census differ, and one file cannot serve both. **Both axes are now split:**

| file | consumer | corpus |
|---|---|---|
| `<key>.txt`, `<key>.depth.txt` | `ast-journal-parity` ctest cell | the running machine's own headers |
| `<key>-sysroot.txt`, `<key>-sysroot.depth.txt` | `journal-sweep-*` | the vendored sysroot |

`verify_ratchet.cmake` takes `JDEPTHFILE` (default: the `JBASELINE`-derived `<key>.depth.txt`, so the ctest cell is untouched); `journal_sweep.cmake` redirects both `JBASELINE` and `JDEPTHFILE` to the `-sysroot` names on every path that is not the host-headers one. Each of the four files enforces hard in its own environment — nothing is shared, and nothing is softened.

This was not theoretical. `arm64-linux.depth.txt` held `fix=30523 deep=10921` from a qemu + stage3-sysroot run, and every arm64 CI cell compiles the corpus with the runner's own headers: 1210 rows / 798671 ops / `fix=31493 deep=10965`, hard-failing 15 jobs × 3 opt levels. All 45 cells — gcc, clang, musl, static, pie, dwarf, sanitize, multisource, cross — reported the identical triple, which is what makes 31493 a measurement and not noise. Note what the two numbers do *not* differ by: the honesty row is the same single `arch/arm64.c myprintf` / 14 raw ops / 688 B on both sides. The i386-win32 ceiling moved the same day for a different reason — a genuinely stale bank, rebanked from real Windows hardware in `ee5cc6a6`; the two corpora agree there, so its `-sysroot` file merely corroborates the ctest one.

**Every baseline now records the corpus that produced it**, which is what makes the next such difference self-diagnosing instead of a false verdict. `.depth.txt` gains `rows=` and `ops=` beside `fix=`/`deep=`; the honesty file gains a leading `#rows=` marker, filtered out of the set comparison so it never becomes a phantom member. Both are **optional** — a file without them behaves exactly as before, which is what keeps the three unreachable-environment banks (`i386-win32`, `arm64-darwin`, `x86_64-win32`, all mingw or macOS) working untouched. When the recorded row count is present and differs from the measured one, the verdict is downgraded from a hard failure to a `NOT COMPARABLE` report naming both corpus figures and telling you to rebank in *that* environment. Had this existed, arm64 CI would have gone green with a precise diagnostic rather than red with a wrong one.

Comparability keys on `rows` alone. `ops` is native-sensitive — a cross run reads ±4 against a native one on several targets (arm64-linux 795236 cross vs 795240 native; x86_64-win32 796735 vs 796731) — whereas `rows` matched cross and native on every key measured, so no sweep mode can trip a false "not comparable". `ops` is carried for diagnosis only.

The generalization this closes: `<key>.depth.txt` pins a GitHub runner's glibc, so an image bump moves it the same way this move did. That is a rebank from the CI log, not a regression — and now the ratchet says so itself instead of reporting REGRESSED.

Three gaps left open on purpose, so the layout documents them rather than hiding them:

- `i386-linux.txt` and `riscv64-linux.txt` have no `.depth.txt` at all (theirs became `-sysroot`), so a native i386 or riscv64 ctest cell would silently skip the depth check. No such cell exists — the qemu CI jobs do not register `ast-journal-parity` — but a `-m32` host build would hit it.
- `x86_64-win32.depth.txt` is byte-identical to `x86_64-win32-sysroot.depth.txt` (`fix=31018 deep=11283`). That is either genuine agreement between the two corpora or a sysroot measurement sitting in the ctest slot. It passes green in the mingw CI cell either way; confirm against a real mingw run before trusting it as an independent figure.
- The three unreachable banks carry no corpus provenance and cannot until someone runs a sweep on mingw/macOS hardware.

#### Standing constraints — binding on every group, do not re-litigate

- Do not journal `vstore` for struct or bitfield operands. Journal replay runs from `ast_func_end`, after block scopes have popped and `sym_free` has clobbered function-local type Syms, so a restored operand's `type.ref` dangles onto the free list and the `VT_STRUCT`, bitfield and `verify_assign_cast` paths chase it — and the crash was invisible to the parity gate because the dying file silently shrank the function census, so watch `fn=` alongside the verdict counts. `jrn_vstore` admits ref-free operands only and `verify_assign_cast` early-outs under `jrn_replaying`.
- Do not journal `vpush_ref` as its own op. Replaying it re-runs `get_sym_ref`, minting a fresh `anon_sym++` and a fresh extern symbol, which changes relocation targets. Record the inner `vpushsym` with the `Sym` already created; `vset`/`vpush64`/`vpushs`/`vpushll`/`vseti`/`vpush`/`vpush_ref` all funnel through `vsetc`/`vpushi`/`vpushsym`.
- `JOP_MKPTR` must record the result type and never re-run `sym_push` at replay — a re-run mints a different Sym and `jrn_sv_eq` compares `type.ref` by pointer, the same lesson as `vpush_ref`. Writing the recorded ref at replay is safe only because every op's issue restores its own recorded vstack snapshot: the written ref is only ever pointer-compared at the next boundary, never dereferenced.
- Do not build a liveness model for the journal. `get_reg` scans exactly `vstack[0..vtop]` and nothing else, so the allocator has no liveness notion to model — the live set IS the vstack, and reconstructing it exactly re-derives allocation for free. Measured on the self-host TU: max registers ever simultaneously live is 7, int pressure never exceeds the 3-register pool, and 99.36% of `get_reg` calls find a free register without spilling. An operand-only (top-two) journal agrees with the real allocator only 94.96% of the time and no fixed window is ever sufficient — the deepest class-matching register sat 11 slots below `vtop`. The fix is exact stack-effect modelling, not live-in/live-out sets.
- `cur_switch` does not read a freed `switch_t` — investigated, no defect found, do not re-open without new evidence. `end_switch` unlinks before freeing (`cur_switch = sw->prev` then `mcc_free(sw)`) and `sw->prev` is live. An instrumented watchlist reported 81 apparent hits that were all allocator address reuse; re-run leaking instead of freeing, it reports zero. The predicate was never observed taking the wrong path in either direction. The real effect is replay-context only: journal replay runs from `ast_func_end`, where `cur_switch` no longer reflects record time, which is journal state rather than a compiler bug. Caveat: `gen_opl` is `#if MCC_PTR_SIZE == 4` so this is measured on `gen_opq`; the i386 site is covered by structural analogy only.
- Inline asm is NOT a raw-blob boundary for the journal — retired 2026-07-31, and this entry replaces the standing constraint that said it was permanent. That constraint conflated the recorder's inability with the journal's: the recorder cannot model inline asm because it would have to re-parse, but `asm_instr` (`src/mccasm.c:1460`) splits cleanly at the `skip(')')`/`save_regs(0)` boundary and the journal only ever needs the emit half. Two ops do it. `JOP_ASM` wraps `mcc_assemble_inline` and records the **post-substitution** template text, so replay re-assembles without re-parsing — `++asmgoto_n` never re-fires because the `LG.<n>` name is already baked into the recorded text and `get_asm_sym` is find-or-create, and asm-goto is the *easy* case rather than the hard one because its labels are relocation-mediated (`put_extern_sym2`, `mccasm.c:1531`) and resolved in `label_pop` *after* `ast_func_end`, so they never touch the `gjmp`/`rsym` chains. `JOP_ASMGEN` wraps the two `asm_gen_code` calls, recording `operands[]`, `clobber_regs[]`, `nb_operands`/`nb_outputs`, `is_output` and `out_reg` into the `jrn_raw` pool; `op->vt` needs no index conversion because `vstack` is `mcc_state->gen_vstack + 1`, a fixed array, so the pointers stay valid across replay. Both call sites are in `mccasm.c`, which sits *below* the `#undef` fence, so they are explicit `#ifdef MCC_JOURNAL_HOOKS` calls rather than macro interposition — the same treatment `gjmp_addr_acs` gets. The only parser hazard is that `mcc_assemble_inline` clobbers `tok`/`tokc`; `JOP_ASM`'s replay saves and restores both. The recorder's own inline-asm item is unaffected and still open.

#### Portable — every target

- **P2** Model `VT_CMP`/`VT_JMP` before attempting any transform that moves emitted code. A pending comparison lives in EFLAGS, occupies no register, can never be spilled (`save_reg_upstack` bails on `r >= VT_CONST`) and there is NO flag-liveness tracking anywhere — correctness today rests on emission order plus `vcheck_cmp()` materialising eagerly on every push/swap/rot/rev. Jump chains are absolute byte offsets threaded through the emitted displacement fields, so any insertion, deletion or motion of bytes between a link and its target silently corrupts them. Constrained by the no-liveness-model entry above: the fix is exact stack-effect modelling.

### Replay_IR

Instruction 36 governs this section. Replay_IR (`src/mccrir.c`, `src/mccrir.h`) is the single model that replaces both predecessors; the *Recorder fidelity* and *Operation journal* sections above stay live and binding until it reaches the deletion bar, and their open items are what it must subsume rather than a parallel effort.

Why neither predecessor can simply become the other, measured and not assumed. The journal is faithful because it derives nothing: `jrn_run` restores a recorded vstack snapshot before every op (`src/mccast.c:15951`) and aborts if `ind` moved by one byte (`:15955`), so 31003 of 795697 op boundaries need a fixup and 86.5% of bodies need at least one. That is a position-locked tape — there is no structure a transform could edit, control flow exists only as absolute jump-chain offsets, and `JrnSub` nesting is diagnostic-only and never replayed. The tree is transformable because it has structure, and declines 182 bodies the journal reproduces. Replay_IR takes capture from the first and structure from the second.

Phase order, each behind the one gate, each byte-identical with it off:

### Optimization levels and the `-O4` search

- Re-decide whether the `-O4` search's exploratory workers should be silent for *errors* too, and whether `-O4` should have its own ctest `-O` axis. The doubled-diagnostic defect is fixed: `mcc_superopt_search` and `mcc_superopt_perfn` spawn one child per candidate configuration and every child re-parsed the TU and re-emitted every diagnostic onto the shared stderr, so a cold-cache `-O4` compile printed each warning 1339 times (a warm `~/.cache/mcc` hid it at 2 — measure this one with a fresh `XDG_CACHE_HOME` per side or the cache decides the answer). The exploratory children now carry `-w` and only the final authoritative spawn, whose object becomes the artifact, is unsuppressed; `cli/o4_search_does_not_repeat_diagnostics` locks `O1=1 O4=1`. Left open: a hard error still prints once per child before the search gives up, and `-O4` remains off the ctest `-O` axis, which is why this stood — the whole `-O6` exec sweep is 146 s at `-j8`, so a bounded cell is affordable if it is wanted.
- Decide whether the out-of-process superopt driver runs at `-O4` at all. On the five-kernel bench it is the best cell on zero kernels, ties on two, and loses 27% on spectral and 25% on matmul; driver-off is greater than or equal to driver-on everywhere, and buys 8-22% `.text` for it. Making it opt-in and shipping the in-process result is a semantic change to `-O4`, so it wants a decision.
- Replace the `text + spills * 48` scoring proxy. It is anti-correlated with speed on two of five kernels. The weight is mid-plateau, so this is the objective, not the tuning.
- Then floor the graft budget. `so_setenv_cfg` writes `inl ? limit : 0u` and `limit = gate >> 4` is 0 for every gate below 16, so every gate with the inline bit clear forces zero grafts — the whole spectral regression on the driver-off path. Both a narrow and an unconditional version fire and are byte-identical on the driver-ON path, so this cannot be measured until the two items above land.
- Make `-O4` a reproducible build. Same source, same flags, matmul differs 25% in instructions between a 577-entry `~/.cache/mcc` and a fresh `XDG_CACHE_HOME`, deterministically within each state.
- Make a memo hit make `-O4` faster. Eight successive compiles of an unchanged input each spend the full 4-second budget to reproduce a byte-identical binary. Add an early-out on a fully-exhausted checkpoint, and bank the `-O3` configuration in the checkpoint record so a hit hands back a real result.
- Say what `-O4` optimises in the help text, or make the axis selectable. `-Os` already exists for size, so users expect `-O4` to be fastest.
- Explain why the static cost model prefers a larger emit at a higher budget (one extra second of search costs 144 bytes at identical runtime, between `-O4` and `-O5`), and why the emit-size objective cannot reach the smaller configuration at all. The driver's accept logic is not at fault.
- Sandbox `so_run_score` or make it explicit-opt-in per invocation before considering `MCC_AST_JITSCORE` as a default. It builds `mcc -run <src>` and executes the user's program three times with no argv at compile time. Runtime scoring is worth 25% of instructions on matmul at nil compile cost.
- Fix the `-O1` `atoi` out-of-line copy. `__OPTIMIZE__` from `-O1` up turns on glibc's `__USE_EXTERN_INLINES`, mcc turns the `gnu_inline` wrapper into `VT_STATIC | VT_INLINE` and emits it out of line, so an un-inlined call reaches a local copy; gcc emits no out-of-line definition. Removes ~52 bytes of dead `.text` from every `-O1`+ TU that includes glibc headers, but it changes identifier binding, so it needs its own validation run.
- `MCC_AST_XMM_HI` is inert for two independent reasons, both measured 2026-07-31 — do not re-open as a gate bug, and do not expect FP promotion to fix it. The gate itself works: with it on, `reg_classes[XMM8..15]` carries `MCC_RC_FLOAT` for all eight. (1) It only affects `get_reg(MCC_RC_FLOAT)`, the SCRATCH allocator, and scratch FP demand never exceeds ONE — instrumenting `get_reg` gives max-simultaneously-live 1 on `fp_builtins.c` (19 allocations), on a `fabs`/`sqrt` accumulation loop (24), and on a loop written to hold 12 doubles live in the source (111). (2) Promotion, the one thing that does use many FP registers, never consults `reg_classes` at all: `ast_promo_xmm_leaf[]` already names 24..31 (the high eight) and replay assigns them by writing `sv.r = preg` directly in the `AST_Ref` case, so the class bit is bypassed. Confirmed by experiment: on an FP-heavy LEAF, `MCC_AST_PROMO_LEAF_XMM` `=0` vs `=1` changes bytes — promotion fires and does use the high registers — while `MCC_AST_XMM_HI` `=0` vs `=1` with promotion ON changes nothing. So the gate would only ever pay if several FP TEMPORARIES were live at once inside one expression, which is a codegen-shape question, not a register-pool one. The arm64 `v8`-`v15` / riscv64 `fs0`-`fs11` callee-saved pool items are about PROMOTION pools and are unaffected by any of this.
- Widen `MCC_AST_REGDISP`: it fires on one of five kernels, and `ast_regdisp_env`'s `!(vtop->r & (VT_SYM | VT_LVAL | VT_MUSTBOUND | VT_BOUNDED))` guard is a wide exclusion. Find why it misses the other four hot loops.
- Replace `ast_now_ms`'s `clock()` with a monotonic high-resolution source (`CLOCK_PROCESS_CPUTIME_ID`, `CLOCK_MONOTONIC` fallback, `uint64_t` nanoseconds), keeping a `clock()` fallback because the asttool harness includes `mccast.c` without the mcchost timer. Coarse resolution makes the stop point land on a different candidate run to run — a dense switch's jump-table dispatch flips between identical runs. Pair it with count-based ordering; precision alone does not restore the AOT==JIT invariant.

### Codegen

- Add auto-vectorization. Packed SIMD exists only in the assembler/disassembler tables; codegen emits zero packed ops and there is no `VT_VECTOR` or intrinsic path. First the backend (x86 `mulpd`/`addpd`/`movupd`/`unpcklpd`, arm64 `fmul`/`fadd .2d`, `ld1`/`st1`, `zip1/2`, a vector register class, a vector AST node the re-emit path lowers), then a straight-line SLP packer as a new AST strategy. Decide `VT_VECTOR` versus an emit-only pack-group annotation, and whether v1 is x86-only. Worth ~1.9x of matmul's gap; the other ~5x is scalar inefficiency.
- Design and implement an aggressive inline-and-register strategy, and start it from an enumerated table of directions rather than a single guess — the design space is wide and the first choice constrains the rest. Two halves. (a) **Inline past the expression-only whitelist.** `ast_inline_node_allowed` admits only value-shaped nodes (`Literal`/`Ref`/`Load`/`Convert`/`Binary`, an address/member `Unary`, a ternary `If`) and `ast_inline_graftable` wants a `BasicBlock` root reaching an `AST_Return`, so a callee carrying a `Jump`, a `Store` or a nested call is uninlinable today. Lower a control-flow callee inline as labels plus jumps to a single join point (`AST_Jump` op 4/5 already model label/goto, `ast_rp_label_get` already allocates replay labels), and promote the callee's frame slots into registers once inlined rather than materializing the caller's stack — the inline site knows the callee's whole live range, which is exactly the information `ast_plan_promotion` lacks at a call boundary. Depends on the `AST_Invoke` live-range split above, and on dead-static elimination for the `MCC_AST_INLINE_STATIC` flip. (b) **Fill idle register slots by rewriting the arithmetic.** When the colouring leaves registers free, rewrite formulas into the representation that uses them: hoist a loop-invariant divisor to a reciprocal multiply, swap `mul`/`div` where the result is bit-identical, and choose an integer or FP register file per expression rather than per type. Hard constraint: `x/c -> x*(1/c)` is bit-identical only when `1/c` is exactly representable (`c` a power of two); everything else changes results and belongs behind fast-math semantics, not behind a register-pressure heuristic — the differential fuzz builds its reference with `-ffp-contract=off -fno-fast-math` and will catch it. Integer `div` already has its mul-high path in `ast_divmagic_*`. Judge both halves on instructions retired, not emitted size: inlining a control-flow callee grows the function by construction.
- Make the `-O4` search preserve register promotion. With gates on, `advance()` has 7 stack memops at `-O2` and 18 at `-O4` for a nearly identical instruction count, because `ast_cost_score` cannot see spills and rates the two orders equivalent. Adding FP registers does not fix it. Same "eligible but the search does not select it" mechanism that keeps `ivsr`, `licm` and the math-inline from firing on `advance()`.
- Split each promotion candidate's live range at `AST_Invoke` boundaries. `has_call` is function-global, so a caller-saved FP register is unusable even for a value that never spans a call. The interval and colouring machinery already exists.
- Add the callee-saved FP pool: arm64 `v8`-`v15`, riscv64 `fs0`-`fs11`. Both backends model only 8 FP registers, all caller-saved, and their `fltr`/`freg` assert `r <= F(7)`, so there is no register id for the high half. Needs the FP register file, `reg_classes`, prolog/epilog ABI save-restore and `get_reg`'s scratch discipline extended. x86_64 SysV has no callee-saved xmm.
- Port `MCC_AST_REGDISP` to arm64, riscv64, i386 and arm: `load`/`store`/`gaddrof` recognition, a per-arch `gen_reg_addi` (LEA-equivalent, flags must survive), and lifting the `#ifdef MCC_TARGET_X86_64` on `ast_regdisp_env`. Then fold array indexing (`a[i].f` and the array-member case the x86_64 slice excludes).
- Promote a value-producing `i++`. The statement form is done; the expression form needs the old value preserved across the update.
- Admit a loop-invariant FP-constant or global-address load to the preheader hoist. `ast_ltemp_scan`/`_materialize` is integer-only via `ast_ident_intt`; gate on `ast_cost_spill`'s FP budget to respect pressure.
- Give the `-O4` search a promotion actuator: `MCC_AST_PROMO_LEAF_CALLEE`/`_LEAF_XMM` plus a bounded `MCC_AST_PROMO_POOL` as `so_axes[]` entries decoded from the budget radix, per-function via a spare `ast_fncfg_parse` bit. A bad pool choice is a miscompile, not a size regression, so restrict the axis to ABI-validated pool sizes and gate acceptance on an exec diff against the seed.
- Implement PC-relative `adrp`+`add` for arm64 local statics — investigation done 2026-07-31, verdict **yes, measured**. `arm64_sym` (`src/arch/arm64/arm64-gen.c:427`) unconditionally emits the GOT sequence (`ADR_GOT_PAGE` + `LD64_GOT_LO12_NC` + a load) for **every** symbol on ELF/Mach-O; only the `MCC_TARGET_PE` branch uses the direct `ADR_PREL_PG_HI21` + `ADD_ABS_LO12_NC`. So a file-local `static` (non-preemptible, defined in the TU) costs 3 insns + a GOT slot + a memory load where 2 insns (`adrp sym@PAGE` / `add sym@PAGEOFF`) suffice; `int bump(void){return ++s_counter;}` at `-O2` on arm64-darwin does the GOT dance **twice** (verified by objdump: two `ADR_GOT_PAGE`/`LD64_GOT_LO12_NC` pairs for one increment). GOTPAGE_LO15 alone is a plain GOT access (like `LD64_GOT_LO12_NC` but a 15-bit page-relative imm); it does not unblock static on its own because 541/542 still error. These relocs never appear in mcc's own output, so adding handlers is purely additive — but getting TLSIE subtly wrong silently corrupts every `errno`/TLS access in the static binary, so it needs the full self-host+qemu bar.
