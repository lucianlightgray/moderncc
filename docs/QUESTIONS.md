### Q-mac-30258 — [mac-arm64] — 2026-08-20T05:30Z — BLOCKS: T-mac-30178
Should mcc bump its predefined `__GNUC__` from 4 to ≥7 (fleet-wide)? Context: mcc HAS the `_Float32`/`_Float64`/`_Float16`/`__float128` type keywords (like gcc≥7) but reports `__GNUC__ 4` (like a pre-7 compiler). glibc's `bits/floatn-common.h` uses `!__GNUC_PREREQ(7,0)` as its proxy for "compiler lacks the _FloatN keyword" and therefore emits `typedef float _Float32;` — which collided with a `_Float32` keyword and broke every glibc `#include` on lin/riscv64 (T-mac-30178, reverted 4ea50353). gcc coexists because gcc≥7 makes glibc SKIP that typedef. Bumping `__GNUC__`≥7 would let glibc skip the typedef (the clean gcc-matching fix) AND unblock adding the `_Float32`/`_Float64` keywords, BUT it also flips many OTHER glibc `__GNUC_PREREQ(7,…)` / `__GNUC_PREREQ(4,…)` feature guards fleet-wide (floatn typedefs, builtin availability, attribute gates) — a broad behavioral change needing cross-target verification, not a blind bump.
**Mode (b): no safe assumption.** T-mac-30178 is BLOCKED — the _Float32/_Float64 keywords stay reverted (build-correct) until this is decided. `__fp16`/`__float128`/`_Float16` keywords already ship (they happen not to collide with a glibc typedef on the tested sysroots — but the same class of risk exists, so the decision generalizes).
**Cost if wrong:** bumping without verification could silently flip glibc feature-macro behavior on lin/riscv64/win (mingw also checks `__GNUC__`) → subtle miscompiles or build breaks across the fleet; NOT bumping leaves `_Float32`/`_Float64` unavailable freestanding/on macOS (a minor C23-interchange-types gap). lin-x64 offered to run the qemu-riscv64+glibc validation leg once scoped.
REF: DETAILS.md#t-mac-30178-float32-keyword-reverted
**DECISION (2026-08-21, user via lin-x64): BUMP __GNUC__ to 7 — VERIFY FIRST.** Land behind cross-target validation (qemu-riscv64+glibc, native lin, win/mingw feature-guard sweep) before fleet adoption; then unblock T-mac-30178 (restore the _Float32/_Float64 keywords). Owner mac; lin offered the qemu-riscv64+glibc leg.


### Q-lin-10456 — [lin-x64] — 2026-08-21T00:45Z — BLOCKS: none (advisory; informs T-lin-10455)
Design direction: how should mcc leverage the runtime JIT cache (the KGC observed-input→output history + graduated-variant registry) to drive an optimization strategy that builds and evaluates PERMUTATIONS/COMBINATIONS of algorithms/machine-code variants (type substitutions, opcode-trick rewrites, algorithm swaps) rather than the current one-variant-at-a-time blind retype? Three sub-questions: (1) **Interface/query surface** — what would software use to interrogate the JIT cache: a queryable table of {function, variant-descriptor (type-subst / gate-mask / opcode-form), observed-call count, hit/miss vs baseline, cost, poison-state}? A generator that enumerates the permutation space (type matrix × opcode tricks × gate subsets) and a scheduler that admits candidates by expected-value given cache history? How do variants compose (a proven type-narrow THEN an opcode-trick on the narrowed form)? (2) **A comprehensive promotion formula over observed I/O** — is there a sound rule to promote a variant to 100%-trusted based on the JIT cache's recorded inputs? Sketch: a variant is promotable when, for every observed input tuple, output==baseline AND the observed input set provably COVERS the variable's live range at its most-recent set site (a VLAT/VRP range-cover proof) — i.e. promote-until-a-new-unknown-input-is-seen-at-the-origin-set-site, where seeing an input outside the proven-covered range at the def site RE-ARMS verification (demotes to shadow-compare). What is the exact invariant tying "observed-inputs cover the range" to "safe for all inputs" (range-cover for monotone/width-bounded ops; NOT valid for precision-lossy int↔float unless the value is provably mantissa-bounded)? (3) **Cache-as-oracle economics** — cost model for how many shadow-compared calls before promotion, poison/demote thresholds, and persisting the proof across runs (the existing kgc-warm tuple reload).
**Assumed for now (mode a):** the current slice keeps the conservative live shadow-compare-forever + poison model (never hard-promotes a blind variant to skip the baseline); safe, just leaves perf on the table. T-lin-10455's remaining work proceeds under this assumption.
**Cost if wrong:** a promotion rule that trusts observed-input coverage without a sound range-cover proof at the set site would hard-adopt a variant that diverges on an unseen input → a real miscompile (not the current always-safe shadow-compare). Getting the invariant in (2) right is the difference between an optimization and a latent wrong-code bug.
REF: DETAILS.md#t-lin-10455-retype-superopt
**DECISION (2026-08-21, user): VLAT-GATED HARD-PROMOTE.** T-lin-10455 adopts hard-promotion (skip the baseline) gated on a VLAT/VRP range-cover proof at the variable's most-recent set site; an out-of-range input at the def site re-arms shadow-compare. NOT the unsound N-clean-calls rule. This is the sound version of "promote until a new unknown input is seen."
